## この判断は何を決めるのか

### 背景

- 基盤フィーチャーと実行系フィーチャーの「設計書」を、今回少し直しました（差し戻しの手当て）。
- このうち基盤の直した部分（必須項目と先送り項目をスキーマ上でどう書き分けるかの取り決め）は、他の4つのフィーチャー（評価・自己改善・論文・統治）が「土台のルール」として使っています。
- ですから「土台を直したら、それを使う側も見直しが要るのでは？」という疑問が出ます。

### ゲートが確認したこと

別プロセスの横断整合ゲートが6機能すべてを突き合わせた結果：

- 今回の直しは**取り決めの「言い方を明文化した」だけ**で、項目の中身（どんな項目が必須か、値の範囲、検証状態の言葉づかい）は**一つも変わっていない**。
- だから、使う側の4機能の文書が今回の直しで矛盾する箇所は**ゼロ**でした。

### 決めてほしいこと

ルール正本には「上流（土台）を直したら下流（使う側）も見直し対象にする」と書いてあります。ただし**「中身が変わっていない明文化だけの直しでも、形式的に見直しフラグを立てるか」までは書いていません**。そこが正本の空白なので、勝手に決めず確認しています。選択肢は2つです。

- **A：形式フラグを立てない（ゲート判定どおり・推奨）**
  - 中身が変わっていないことはゲートが確認済み。下流4機能のメタデータ（spec.json）には手を触れず、「波及ゼロ」を証跡に記録するだけにして、設計の人間再承認へ進む。
  - 利点：不要な見直し作業や状態の巻き戻しが発生しない。実態（中身不変）に即している。
- **B：念のため形式フラグを立てる**
  - 手戻り種別の「迷ったら上流寄りに倒す」という保守原則に倣い、下流4機能のspec.jsonに見直しフラグを立てる。
  - 欠点：中身は変わっていないので実質意味のある再レビューは生じないのに、spec.json変更（明示承認が必要）と下流の進行状態の巻き戻しだけが発生する。

私の推奨は**A**です。理由は、ゲートが「中身の波及ゼロ」を独立に確認しており、Bは実態のない手続きコストと状態の巻き戻しだけを生むためです（保守原則は「手戻り種別の判定に迷うとき」のもので、中身不変が確認済みの今回には当てはまりません）。

## 一般的なやり方（プロンプトを減らす順）

1. **編集の自動承認＋安全な許可リスト** ファイル編集を自動承認（acceptEdits、本プロジェクトで設定済み）にし、安全な読み取り系コマンドの前置きを許可リストに積む。最も手軽で、本プロジェクトも今ここにいます。
2. **PreToolUse フック（実行前フック）で自動判定** 許可リストの「前置き一致」では書けない条件（例：「`git clean` は `experiments/` 配下だけ自動許可、それ以外は確認」）を、コマンドを検査して許可/拒否を返す小さなスクリプト（フック）で表現する。多くの自動実装プロジェクトはこれを使い、危険な操作だけ確実に止め、それ以外は無確認にしています。グロブの限界を越えられる本命の方法です。
3. **サンドボックス＋ほぼ全自動** OSレベルで書き込み先・ネットワークを制限した隔離環境（サンドボックス）で動かし、確認をほぼ全部スキップ（bypassPermissions）。誤操作してもサンドボックス外に影響が出ないので安全網を環境側に移す方式。使い捨てコンテナや専用作業ツリーで回す自動実装でよく使われます。
4. **ヘッドレス／CI実行** 対話なしモード（`claude -p` や Agent SDK）で、使えるツールと権限モードを起動時に固定し、ブランチ隔離＋小まめなコミットで「失敗しても戻せる」状態にしてPRレビューで担保。完全無人運用の定番です。

## 何が本当の問題か

毎回フックの正規表現をいじる、置き場所を変える、というのは対症療法です。根っこは「長時間・無人で進める作り直し作業」と「1コマンドごとに人が確認する安全モデル」が構造的に噛み合っていないことです。確認プロンプトは「取り返しのつかないことを防ぐ」ことの弱い代用にすぎず、これを継ぎ足し続けると、おっしゃるとおりいつか事故ります。

## 発想の転換：可逆性を「仕組み」で保証する

本当に取り返しがつかないのは次の3つだけです。

- リポジトリ外への操作（/tmp などプロジェクトの外）
- 履歴の書き換え・公開（git push、reset --hard、rebase、force-push）
- コミットしていない作業の破壊

逆に言うと、リポジトリ内の追跡済みファイルへの変更・削除は、git でいつでも元に戻せます。旧 v1 を rm しても履歴から復元できます。つまり「リポジトリ内かつコミット済みの土台がある」状態なら、自動作業がどれだけ激しくても破滅は起きません。

そこで安全網を「1コマンドごとの確認」から「可逆な実行範囲（envelope）」へ移します。

## 提案する原則（一度決めて文書化、以後ぶれない）

- 自動許可：効果がリポジトリ作業ツリー内に収まり、git で復元可能なもの（rm 含む。土台コミットがあるから可逆）
- 確認必須：リポジトリ外に出る／履歴を書き換え・公開する（push・reset --hard・rebase・force-push・プロジェクト外パス）

この原則なら特殊ケースの継ぎ足しが要りません。
