## 1. 問題点の整理

### 1.1 3 つの軸が混在している

本対象システム（dual-reviewer）の原典レビュー記録では、本来独立した 3 つの軸が、フェーズによって異なる語彙で記録され、軸自体も混同された状態にある。

3 軸とは：

- **重大度**（severity）：所見の深刻さの段階
- **対応優先度**（action priority）：そもそも対応するか否か
- **手戻りの深さ**（depth）：対応がどこで吸収されるか（同フェーズ内／上位フェーズへの差し戻し）

### 1.2 フェーズごとの語彙（現状）

| フェーズ | 重大度 | 対応優先度 | 深さ |
|---|---|---|---|
| 要件 | CRITICAL／ERROR／WARN／INFO（4 段階） | must-fix／should-fix／leave-as-is（3 段階） | 原典に明示なし |
| 設計 | CRITICAL／ERROR／WARN／INFO（4 段階） | must-fix／should-fix／leave-as-is（3 段階） | 原典に明示なし |
| タスク | 致命／重要／軽微（3 段階） | must-fix／should-fix／leave-as-is（3 段階） | 原典に明示なし |
| 実装適合 | 致命／重要／軽微 または P1／P2／P3（3 段階） | 原典に独立語彙なし（重大度で代用） | A／B／C／D（実装段起点のみ） |

### 1.3 不整合の具体例

- **重大度の段階数の不揃い**：要件・設計は 4 段階、それ以外は 3 段階
- **対応優先度の欠落**：実装適合段にだけ独立の対応優先度語彙がなく、重大度がその代用になっている
- **深さの偏在**：実装適合段にだけ A／B／C／D の深さ表記があり、他段は暗黙
- **軸の混同**：例えば must-fix は対応優先度の語彙だが、本論文 §3.3 では「must-fix／should-fix は X-0（段内吸収）に対応する」と書いており、対応優先度と深さを同列に扱ってしまっている

### 1.4 評価への影響

- フェーズ間の所見数を同じ尺度で比較できない（重大度語彙が違う）
- 「対応すべき所見」の集計に、フェーズによって異なる定義が混ざる
- 深さの分布を全フェーズで描こうとすると、4 段中 3 段で原典記録がない
- 統計的な評価（重大度別件数の推移、対応優先度別比率など）が、フェーズによって意味が変わってしまう

## 2. 統一の方向（今後の予定）

### 2.1 3 軸を独立に明示する

各所見が 3 つの軸の値をすべて持つ構造に統一する：

- **重大度**：3 段階に統一（High／Medium／Low）。原典の 4 段階（CRITICAL／ERROR／WARN／INFO）は粗統一する（INFO を WARN と統合して Low に）
- **対応優先度**：3 段階に統一（must-fix／should-fix／leave-as-is）。実装適合段にも導入する
- **深さ**：本論文 §3.3 で定義した二次元表記（起点フェーズ記号 N／R／D／A／I ＋ 深さの数字 0／1／2／3／4）を全フェーズに統一

### 2.2 統一後の所見記述例

各所見が次のような構造を持つ：

- 重大度：High／Medium／Low のいずれか
- 対応優先度：must-fix／should-fix／leave-as-is のいずれか
- 深さ：R-0／R-1／D-0／…／I-4 のいずれか
- 他機能波及：あり（対象機能名）／なし
- 内容：所見の本文

### 2.3 既存原典との対応関係

新形式を導入しても、原典記録は git に保全されているため不変扱い。新形式での再記録は次バージョン以降のレビューから適用する。既存記録の遡及変換は不要（必要時には v2 抽出のような変換文書を別途作る）。

## 3. 実装案の課題（次バージョンで策定）

本論文 §6.3「新表記に基づく実装の再整備」に書いた 3 つの組み込み先について、実装案の策定そのものが次バージョンの最初の作業となる。

### 3.1 レビュー記録テンプレート

要件・設計・タスク・実装適合の各レビュー記録テンプレートに、3 軸を必須項目として組み込む。

- 必須項目／任意項目の設計
- 必須項目の検証規則（語彙の有効値、深さ記号と起点フェーズの整合）
- 既存テンプレートとの互換性（移行戦略）

### 3.2 機械抽出コード

ログから 3 軸の値を機械的に抽出するコードを書き、集計用の中間表現（JSON など）に変換する。

- パーサの方針（テンプレートに沿った構造化、表記揺れの吸収）
- エラーハンドリング（不正な深さ記号など）
- 集計時の中間表現の設計

### 3.3 ワークフロー管理機能の検査対象

ワークフロー管理機能の独立再導出で、3 軸の整合性を機械的に確認する。

- 重大度の語彙が定義範囲内か
- 対応優先度の語彙が定義範囲内か
- 深さ記号が起点フェーズと整合するか（例：要件レビューで I-0 が出てはいけない）
- fail-closed 条件の明示

### 3.4 実装案策定の作業

各組み込み先について、具体的な設計案を文書化する作業が必要。

## 4. 本論文（論文 1）での扱い

本論文では現状の 3 軸混在を **限界として記述** している。具体的には §5 第五の限界として「実装段からタスク段への差し戻し記号 I-1 が原典に欠落」を明記しているが、本ドキュメントで述べる 3 軸の混在そのものの解消は、論文 1 では扱わない。

論文 1 の評価部分（§4.3 図 1、§4.6）は、現状のフェーズ別語彙を High／Medium／Low の粗統一で扱う暫定方式で進める。
