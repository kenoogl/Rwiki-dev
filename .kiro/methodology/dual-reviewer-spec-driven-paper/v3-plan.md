# v3 future plan — artifact-to-spec conformance evaluation

_作成: 2026-05-13_
_最終更新: 2026-05-13_
_status: draft v0.1_
_purpose: 実装完了後に生成物を意図・要件・設計・タスクと照合する評価を計画として記録する_

---

## 1. 目的

`dual-reviewer` の方法論において、実装が完了した後に、生成された成果物が当初の意図、要件、設計、タスクと一致しているかを照合する評価を導入する。本文書は、その評価の枠組みを計画として記録するものである。

実装してみると、上位の意図や設計に対して中間ステップが増えたり、解釈がわずかにずれたりすることがある。一方で、単に動作するかどうかや、エラーが出ないかどうかを確認するだけでは、こうしたずれは捉えきれない。したがって、生成物と上流文書の照合を別段階として持つ必要がある。

---

## 2. v2 との関係

本計画は、現在進行中の `dual-reviewer v2` の完了条件には含めない。v2 では次の範囲を扱う。

- 実行層を作り直す
- ケース固有の規則をコードの外に出す
- 3 つのトラック（intent、spec、implementation）を共通化する
- pilot を再取得する

v3 は、v2 が一段落した段階で改めて検討する未来段階の計画として位置づける。

---

## 3. 評価対象

照合の対象は、少なくとも次の 3 項目とする。

### 3.1 意図への適合

実装が、最上位の意図（intent = 開発の起点となる狙い）を壊していないかを確認する。具体的には、意図で示された目的、制約、優先順位が、実装の振る舞いの中で保たれているかを照合する。

### 3.2 開発文書への適合

要件（requirements）、設計（design）、タスク（tasks）で決めたことと、実装が食い違っていないかを確認する。食い違いが見つかった場合は、

- 実装側を直す
- 文書側を更新する

のどちらが適切かを判断材料として残す。

### 3.3 実装で得た知見の文書への戻し

実装中に初めて分かった知見が、コードだけに閉じ込められていないかを確認する。たとえば、観測の単位を型付けする必要があった、特定の境界条件を明示する必要があった、といった知見は、コードの修正だけで終わらせず、上流文書へ反映する。

---

## 4. 位置づけの候補

v3 を実際に導入するとき、次の 2 つの位置づけのうちどちらを採るかは、v3 着手段階で決定する。

### 4.1 既存ワークフローの gate として追加する案

`implementation` の段階の後に、新たな gate を 1 つまたは 2 つ追加する。

- `spec conformance review`（仕様との照合レビュー）
- `intent conformance review`（意図との照合レビュー）

既存のワークフローに沿うので導入の影響は局所的に収まる一方、gate が増えることで全体の流れが長くなる。

### 4.2 別 feature として起こす案

照合評価を独立した feature として立ち上げる。たとえば次のような名称が考えられる。

- `dual-reviewer-implementation-conformance`
- `dual-reviewer-intent-conformance`

feature として独立させると、評価の設計と実装に専念できる一方、既存ワークフローとの接続点を別途設計する必要がある。
