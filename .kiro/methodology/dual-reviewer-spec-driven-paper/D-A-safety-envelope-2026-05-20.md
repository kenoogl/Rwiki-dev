## 0. 安全封筒とは何か

**安全封筒（safety envelope）**：部分的に自律実行される作業を、(1) 復元点をリポジトリに固定し、(2) 使い捨ての隔離環境で作業し、(3) 境界だけを人間が承認する、という3要素で囲む運用作法。本リポジトリでの仕様駆動開発の自己適用で繰り返し用いられ、再実装サイクルと再レビューを安全に進める基盤として機能した。

3要素：

- **復元点**：本ブランチで作業前にコミットしてリモートへプッシュする。万一の問題発生時に「リモート＝確定状態」へ戻せる保証
- **使い捨て隔離環境**：git の「分離作業域（worktree）」で別ブランチ・別ディレクトリを開き、自律実装はそこで完結させる。気に入らなければ作業域ごと破棄して完全復元可能
- **境界のみ人間承認**：本ブランチへの取り込み・コミット・プッシュ・spec.json 書込・フェーズ移行・設計差し戻し判断の各境界では必ず人間が承認する。それ以外（実装の per-task 進行・TDD の赤→緑・テスト追加など）は止めずに自律進行

## 1. 運用の標準手順（自己適用で確立した型）

5機能のスクラッチ再実装と統治の部分修正で繰り返し実施された手順を、操作の連鎖として明文化する。

### 1.1 復元点の固定

- 本ブランチで未コミットの作業を確認し、必要なら commit ＋ push
- リモートの最新コミットが「失敗時に戻る点」

### 1.2 分離作業域の開設

- `git worktree add <パス> -b <一時ブランチ名> <基点コミット>` で別ブランチを別ディレクトリに切り出す
- 基点コミットを明示固定（最新の本ブランチ HEAD など）し、後で「どこから派生したか」を追跡可能にする
- 分離作業域内には承認済み仕様（`.kiro/specs/<機能>/{requirements,design,tasks,spec.json}`）を含めるが、旧 v1 実装は別途意識して破棄方針を立てる

### 1.3 自律実装（per-task 進行）

- 承認済み仕様と再確定設計から各タスクを依存波順で TDD（赤→緑、実装中はテスト不変）で構築
- 実装の途中で per-task の確認を求めず連続進行（実装フェーズ自律規律）
- テストが承認仕様を誤符号化していた場合のみ仕様準拠へ是正する（誤テストに実装を歪めない）

### 1.4 独立適合レビュー

- 完成後、別プロセス（独立サブエージェント）で承認仕様＋実 artifact を照合する独立適合レビューを実施
- レビュー結果は `dual-reviewer-rebuild/.kiro/specs/<機能>/reviews/implementation-conformance-review-*.md` に保存
- GO 可・要手戻り・スクラッチ再実装推奨 の判定を独立に決定

### 1.5 本ブランチへの取り込み（境界承認）

- 分離作業域でコミットしたうえで、本ブランチに戻り `git checkout <commit> -- <対象パス>` で必要ファイルだけを取り込む
- 旧 v1 実装の物理削除（`git rm`）は本ブランチで実施
- 1コミットにまとめて push（境界承認）

### 1.6 分離作業域の破棄

- 取り込み完了後、`git worktree remove` で作業域を破棄
- 旧ブランチも不要なら削除
- ハーネス管理の作業域はロック中のものもあるため、放置で自動回収される場合もある

## 3. 境界承認の運用詳細

人間が承認する境界は次のとおり明確化されている。境界は省略・自動化せず必ず人間が判定する。

- **コミット**：本ブランチへの取り込みコミットは必ず人間承認後
- **プッシュ**：コミットしたらプッシュも同じく人間承認
- **spec.json 書込**：phase 値（requirements-approved／design-approved／tasks-approved／implementation-conformance-reviewed など）の書き換えは必ず人間承認
- **フェーズ移行**：requirements → design → tasks → implementation の進行は人間承認
- **設計差し戻し判断**：適合レビューで手戻り種別 B（設計）／C（要件）／D（意図）が出た場合の差し戻し可否は人間承認
- **approach の選択**：スクラッチ再実装か部分修正かといった作業方針の選択は人間承認（恒常指示が硬い制約であることと整合）

境界の外（実装の per-task 進行、TDD の赤→緑、テスト追加、依存波順の判断、分離作業域内のコミット）は止めずに自律進行する。

## 4. 安全封筒が支えるもの

本リポジトリでの自己適用を通じて確認された効用：

- **復元可能性**：分離作業域は破棄可能で、リモートの確定状態へ戻せる。失敗のコストが低く、再試行を恐れない判断ができる
- **責任の所在**：境界承認の場面が限定されることで、人間が「どこで判断したか」が記録から追跡できる
- **自律性と検証可能性の両立**：境界の外では大規模言語モデルが連続進行し、境界では人間が形式合格と実体妥当性を最終確認する
- **多重独立化との相補**：分離作業域での自律実装と、別プロセスの独立適合レビューが結合することで、合格演出に対する耐性が高まる

## 5. 限界と注意点

本作法は万能ではない。次の限界を明記する。

- **境界承認は依然として人間の判断品質に依存する**：人間が承認時に十分検査しなければ、合格演出を見逃しうる。安全封筒は人間の見落とし自体は防がない
- **分離作業域の基点を明示固定しないと再現困難**：基点を明確にしておかないと「どの状態から作業したか」が後追いできない
- **使い捨て隔離環境の管理コスト**：分離作業域が複数同時に存在する状況では、命名・破棄のルールが必要
- **「自律実行」の範囲は事前に合意される必要**：何が自律で良くて何が境界かを事前に決めないと、境界が曖昧化し承認が形骸化する
- **本リポジトリは N=1 の自己適用**：本書の運用記録は他プロジェクトへの直接適用を保証しない（評価・転用は将来課題）
