# v2 取得方法の設計

_最終更新: 2026-05-13_

## この文書の役割

dual-reviewer v2 の取得処理を、規則ファイル照合（v1 の方式、汚染の原因）から実 LLM 呼び出しに置き換えるための設計判断を記録する。

本文書は議論の進行とともに更新する。各セクションは「決定済み」「議論中」「未着手」のいずれかの状態を持つ。

## 1. 役割設計

- 状態：議論中

### 1.1 比較構造

決定：v1 と同じ 3 方式の比較構造を維持する。

- `single`（単独）：主役のみが走る。
- `dual`（二重）：主役 + 敵対役が走る。判断役は介在しない。
- `dual+judgment`（二重+判断）：主役 + 敵対役 + 判断役の 3 役。

汚染が判明したのは規則ファイル経由で件数が固定されていたためであり、比較構造そのものの善し悪しはまだ評価できていない。v2 では実 LLM 呼び出しに置き換えたうえで、3 方式間の差を改めて観測する。

### 1.2 将来計画として保留する選択肢

次の 2 案は v2 には含めず、v2 の取得が一段落した段階で別途検討する。

- 比較軸を「役割の数」ではなく「モデル間 / プロンプト間 / 温度間」など別軸に変える設計案。
- 役割間を対話形式（複数往復のやり取り）にする通信構造案。

### 1.3 各役割の責務と通信構造

#### 1.3.1 通信構造

決定：逐次方式。

- 主役（primary reviewer）が先に走る。
- 敵対役（adversarial reviewer）は主役の出力を見たうえで、反論や別観点を追加する。
- dual+judgment 方式の場合、判断役（judgment reviewer）が最後に最終判断を付ける。

理由：実運用に近く、敵対役が主役の弱点を狙えるため発見の質が上がる可能性がある。

#### 1.3.2 各役割のモデル割り当て

##### 主役と敵対役のモデル

決定：異なる版を使う。主役 = Opus、敵対役 = Sonnet。両者とも別セッションで運用する。

理由：v1 の経験で、別セッションでも同じ版だとバイアスが出ることが確認されているため、異なる版を選ぶ必要がある。

##### 温度設定

決定：両者とも温度ゼロ。

理由：再現性を優先する。ばらつきの観察は反復取得（後段）で扱う。

##### 判断役のモデル

決定：主役と同じ Opus を使う。ただし別セッションで運用する。

理由：v1 のバイアス問題は「同じ会話文脈での自己評価」が原因であり、別セッションで文脈を遮断すれば同じ版でも独立判断が保てることが v1 の経験で確認されている。

#### 1.3.3 各役割の責務

##### 1.3.3.1 件数指示

決定：下限のみ + 優先順位指示。

具体：各役割への指示として「少なくとも 1 件は挙げよ。上限なし。重大さの順に並べよ。」を含める。

理由：上限を設けないことで、v1 で起きた件数固定化（汚染の根本原因の一つ）を避けられる。下限を置くことで空回答を防ぐ。順位指示は、判断役による整理を行いやすくする。

##### 1.3.3.2 主役の責務

- トピック誘導：大まかなカテゴリだけ示唆する。具体：プロンプトに「正確性 / 安全性 / 互換性 / 保守性」のような一般カテゴリを 1 行で示し、具体内容は LLM に委ねる。理由：完全自由より整理されるが、ドメイン固有指定による汚染再現リスクを避けられる。
- 入力範囲：対象 + 直上の上流。具体：意図段階は `intent.md` + canonical source（あれば）、仕様段階は spec + `intent.md`、実装段階は実装コード + 上流仕様一式（requirements / design / tasks）。理由：上流との整合性指摘が可能で、コストと汚染リスクのバランスがよい。
- 出力構造：構造化（中程度）、Markdown 形式。具体：各発見が 4 フィールドを持つ。重大さ（high / medium / low）、対象箇所（ファイル名と行番号、または該当箇所の引用）、説明、根拠。理由：フィールド固定で集計や比較がしやすく、温度ゼロとの相性も良い。

##### 1.3.3.3 敵対役の責務

- トピック誘導：誘導なし。具体：プロンプトに「主役が見落とした重要問題を挙げよ」とだけ指示する。トピックカテゴリは示唆しない。理由：主役が大まかなカテゴリ誘導付きでレビュー済みのため、敵対役は誘導なしで広い視点から見落としを拾う。
- 入力範囲：主役と同じ入力（対象 + 直上の上流）+ 主役の出力。理由：β 逐次方式と整合し、敵対役が主役の弱点を狙えるようにする。
- 出力構造：主役と同じ 4 フィールド（重大さ、対象箇所、説明、根拠）+ 種別フィールド（反論 / 独立発見）を追加。理由：敵対役固有の役割を分類でき、後段の判断役や集計で活用しやすい。
- 主役への対応スタンス：反論と独立発見を別パートとして分離して出す。具体：出力を「主役発見への反論」「独立発見」の 2 パートに分ける。理由：何が反論で何が独立発見かを後段の判断役や集計で明確にできる。

##### 1.3.3.4 判断役の責務

- 判断方針：トピック誘導はせず、判断の具体的な指針を示す。具体：プロンプトに「重要なものを残し、弱い指摘や重複に注記を付ける」のような判断指針を示す。理由：判断役は「整理する役」なので、項目誘導より判断作業の指針が適切。
- 入力範囲：主役の入力 + 主役の出力 + 敵対役の出力。理由：β 逐次方式と整合し、判断時に元コンテキストも参照できる。
- 出力構造：主役・敵対役の発見リストに、判断ラベル（must-fix / should-fix / leave-as-is など）と判断の根拠を注釈として付与する。発見数は変えない。理由：発見数を維持するほうが研究の観測がきれい。重複や弱さの判定はラベルで残す。
- 主役・敵対役発見への対応スタンス：全発見を残し、ラベルと根拠だけ付ける。理由：研究としては発見の保持を優先。

### 1.4 役割の独立性と呼び出し設計

#### 1.4.1 呼び出し方式

決定：3 役とも別セッション。メイン LLM は 3 役のいずれにもならない。

具体：主役は Opus の別セッション。敵対役は Sonnet の別セッション（β 逐次方式に基づき、主役の出力を入力として受け取る）。判断役は Opus の別セッション（主役の入力 + 主役の出力 + 敵対役の出力を入力として受け取る）。

理由：v1 では主役がメイン LLM そのものだったため、対話文脈や開発履歴の影響でレビューが歪んだ。別セッションでクリーンな文脈にすることでこの問題を回避する。

#### 1.4.2 方式間の再利用

決定：再利用する。

具体：single = 主役 1 回。dual = single の主役出力 + 敵対役 1 回。dual+judgment = dual の出力 + 判断役 1 回。1 ケースあたり合計 3 回の呼び出しで 3 方式すべてを構成。

理由：温度ゼロ前提で理論上同じ出力になるはずなので、コスト効率がよい。3 方式の差を「役割追加の効果」として読みやすい。

#### 1.4.3 セッションの運用形態

決定：Claude モデルを使う場合は方式 B（`claude --print` などの CLI）。別 LLM モデルを使う場合（将来）は方式 D（API 直接呼び出し）。

具体：v2 は Claude 系（Opus と Sonnet）だけを使うので、運用上は方式 B が中心。方式 D は、将来の別モデル比較（1.2 節の将来計画）の準備として方針を残す。

理由：方式 B は自動化とバッチ取得が可能で、SDK 学習が不要。方式 D は最も低レベルだが、別 LLM プロバイダ（GPT 系など）を使うときに必要。

## 3. 入力設計

- 状態：原則決定（実装詳細は実装段階）

### 3.1 ケース文脈の提供

決定：中間案。ケース名は伝えるが、ドメイン情報や期待される問題分野は伝えない。

理由：完全ブラインドだとドメイン特有のリスクを拾えない可能性があるが、過度の文脈提供は結果先取りに繋がる。中間案でバランスを取る。

### 3.2 入力ファイルの渡し方

決定：構造化区切り方式。`<file path="...">...</file>` のような区切り付きで複数ファイルを明示する。LLM の Read ツール呼び出しは介在させない。

理由：再現性が高く、機械的なパースもしやすい。インライン相当の再現性を保ちつつ、ファイル境界が明確になる。

### 3.3 実装段階に委ねる項目

次の項目は実装段階で確定する。

- システムプロンプトとユーザプロンプトの使い分け
- 最大トークン数の設定
- プロンプト文言の正確な表現
- ケース名の具体的表記
- 区切りタグの具体形式

## 4. 出力設計

- 状態：原則決定（実装詳細は実装段階）

### 4.1 保存形式

決定：両方併記。Markdown と構造化（JSON）を両方保存する。

理由：人間が読み返す用途には Markdown、集計や比較の用途には JSON。同じ内容を別形式で保持するだけなのでサイズ増加は小さい。

### 4.2 メタデータの必須項目

決定：全項目を必須とする。各取得の出力に次の 10 項目を必ず付ける。

- `run_id`：取得ごとの一意な識別子
- `timestamp`：取得時刻
- `case_id`：ケース名
- `mode`：single / dual / dual+judgment
- `role`：主役 / 敵対役 / 判断役
- `model_version`：使ったモデルの版番号
- `temperature`：温度設定
- `input_hash`：入力ファイル群の hash
- `prompt_version`：使ったプロンプトテンプレートの版
- `acquisition_design_version`：v2-acquisition-design.md の版

理由：研究データとして全項目が必要。記録コストは小さく、後から「何が記録されていなかったか」で困らないようにする。

### 4.3 実装段階に委ねる項目

- JSON スキーマの具体定義
- Markdown テンプレートの正確な構造
- ファイル命名規約
- メタデータの記録形式（YAML フロントマター / 別ファイル / DB など）

## 5. 取得反復

- 状態：原則決定（実装詳細は実装段階）

### 5.1 取得回数

決定：各設定で 3 回ずつ繰り返す。

理由：temperature ゼロでも実際にはばらつくことがあるため、再現性の実測ができる。コストは 1 回の 3 倍に収まり、ばらつき観察に十分。

### 5.2 ばらつきの観察項目

決定：全フィールド一致。件数 + 内容 + 各フィールド（重大さ、対象箇所、説明、根拠）の一致を観察する。

理由：出力が構造化されているので、全フィールドの一致を観察するのが自然。

### 5.3 失敗時の処理

決定：自動リトライあり。軽微な失敗時は最大 3 回まで再試行し、それでも失敗したら記録して捨てる。

理由：軽微な失敗（タイムアウト、一時的なエラー）を自動回復しつつ、永続的な失敗は別途解析できるよう記録に残す。

### 5.4 実装段階に委ねる項目

- リトライ実装の詳細（待機時間、バックオフ戦略など）
- ばらつき計測の具体アルゴリズム（文字列一致 / 構造一致 / 意味一致など）
- 失敗判定の閾値（タイムアウト時間など）

## 6. 運用

- 状態：原則決定（実装詳細は実装段階）

### 6.1 利用量・速度上限

決定：方式ごとに上限を意識する。

- 方式 B（Claude Code CLI）利用時：subscription プランの利用枠と rate limit を意識する。利用枠を使い切らないようバッチサイズと取得間隔を調整する。
- 方式 D（API 直接呼び出し）利用時（将来）：API コスト上限を設定し、超過時は停止する。

理由：v2 は方式 B 中心のため従量制 API コストは発生しないが、subscription 利用枠を超えると取得が止まる。方式 D を採用する将来時点では API コスト上限が新たに必要になる。

### 6.2 ログ粒度

決定：詳細ログ。各 LLM 呼び出しの入出力全体を保存する。中間も含めすべて記録する。

理由：研究データなので、後で「あの取得は実際に何を入出力していたか」を確認できるようにする。サイズは大きいが、研究の透明性に必要。

### 6.3 並列実行

決定：完全逐次。1 ケース 1 取得ずつ、順番に行う。

理由：研究データ取得では速度より管理容易性とコスト把握の明確さを優先する。並列にすると失敗時の解析やコスト追跡が複雑になる。

### 6.4 実装段階に委ねる項目

- subscription 利用枠の監視方法（取得前のチェック、警告のタイミングなど）
- 具体的な上限額（方式 D 採用時）
- ログ保存方式（ファイル / DB / オブジェクトストレージなど）
- 中断・再開機構
- 監視方法（取得進捗、失敗率、コスト推移の可視化）

## 7. 結果保存

- 状態：原則決定（実装詳細は実装段階）

### 7.1 配置場所

決定：v2 専用パス。`experiments/v2/` や `experiments/protocols-v2/` のように v2 と明示した新しい場所に置く。具体的なパスは実装段階で確定する。

理由：v1（archive）と v2 が明確に分離され、論文記述でも参照しやすい。

### 7.2 archive との関係

決定：対比あり。v1 archive を参照しながら、v2 結果との対比を論文や設計書に書く。archive のパスは現状のまま、参照のみ行う。

理由：論文の核心が「v1 の汚染を発見し v2 で真の値を取得」になる場合、対比は必須。

### 7.3 ディレクトリ構造の原則

決定：トラック別優先。`{v2 root}/{track}-track-runs/{case}/{mode}/...` のような階層。

理由：v1 と階層が揃うので比較しやすく、過去の取得スクリプトの構造とも整合する。

### 7.4 実装段階に委ねる項目

- 具体的なパス名（`experiments/v2/` か `experiments/protocols-v2/` か）
- ファイル命名規約
- 集計サマリの場所
- 過去の取得スクリプトとの統合方法
