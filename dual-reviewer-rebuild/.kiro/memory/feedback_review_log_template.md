レビュー中に利用者へ提示するメッセージは、ラウンド単位で構造を統一する。ラウンドの所見提示と、ラウンド完走時の完了報告という 2 種類のテンプレートを用意し、利用者が読みやすく判断しやすい形に整える。

**Why:** ラウンドの構造を毎回別の書き方で提示すると、利用者は「今どこを判断すべきか」「何件採用し何件見送ったか」を読み解く手間がかかる。テンプレートを統一すれば、見出しと節構造から判断対象を即座に把握できる。

## 所見の二つの分類との関係

本ファイルは「所見をどう見せるか」という形式の規律である。
所見の中身に何を書くか（箇所・現状・問題・修正後）は、別ファイル `feedback_finding_4elements.md` の観点規律で定める。

両者は場面で使い分ける。

- レビュー記録ファイルに事実を残す場面では、四要素（箇所・現状・問題・修正後）で書く。
- 利用者に判断を仰ぐメッセージとして提示する場面では、本ファイルの「概要・問題点・選択肢・推奨」の流れで並べる。
- 同じ所見を両方の場面で扱うときは、まず四要素で事実を残し、提示時に「概要・問題点・選択肢・推奨」の並びへ組み替える。

**How to apply:**

## ラウンド提示テンプレート

    # ラウンド N（観点名） 検出 件数

    ## 概要
    1〜2 文：何のレビューか、利用者に求める判断、判断しないと何が止まるか

    ## 検出 1：所見 ID + 短い見出し
    ### 概要 / 問題点 / 選択肢（案 a / 案 b / ……、案の数は所見ごとに可変） / 推奨

    （検出 2、3、... 同じ構造）

    ## 推奨まとめ
    - 検出 1：案 (a)
    - 検出 2：案 (b)
    - 検出 3：案 (c)（例として、3 案以上から選んだ場合）

注：上記の検出 1 件分のひな形は、利用者に判断を仰ぐ場面の並び。
レビュー記録ファイルへ事実を残す場面では、四要素（箇所・現状・問題・修正後、別ファイル `feedback_finding_4elements.md`）で書く。

## ラウンド完了報告テンプレート

    # ラウンド N 完走

    検出（主役 N 件 + 敵対役 M 件） ＝ K 件採用 + L 件見送り

    修正内容：
    - 検出 1（案 X）：1 文で何を変えたか

    コミット：
    - hash1 ＝ 設計書修正
    - hash2 ＝ 履歴

    次：ラウンド N+1（観点名）着手？

## 提示メッセージに含めない要素

- 内部運用の技術用語や検証手法名 → ログ（artifact）のみ
- 敵対役レビューでの各選択肢ラベルの詳細 → ログのみ
- パターン分類のコード番号や内部運用通番
- 修正規模の細かい数値（+X -Y +Z など）
- ブランチの正式名称（「今回の作業ブランチ」で十分）
- 方法論や運用そのものの長い説明

これらは利用者の判断には不要で、提示メッセージを長くするだけで読み手の負担を増やす。詳細はレビューログ（artifact）側に残し、提示メッセージは判断材料のみに絞る。
