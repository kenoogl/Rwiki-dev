> 用語：主役・敵対役・判定役の定義は `CONVENTIONS.md` 節 8 を正本とする。

レビュー所見（finding、主役・敵対役・判定役の 3 役レビューで挙がった指摘事項）を利用者に提示する場面では、各所見を 4 要素「箇所・現状・問題・修正後」で書く。抽象 1 行（「X と Y が乖離」「文言齟齬」「整合不全」など）では不可。修正前・修正後の actual text を具体引用として必ず含める。

**Why:** 過去に、複数の所見をクラスター単位で集約しただけの提示や、「箇所 + 1 行で何を直すか」だけの提示で、利用者から「分かりにくい」との指摘を連続して受けた。各所見の表示が抽象的だと、利用者が「これは具体的に何の問題か」を自分の頭で再構成する手間が残ってしまう。修正前後の具体引用を含めることで、その手間をゼロにできる。

**How to apply:**

## 提示時の並びとの関係

本ファイルは「所見の中身に何を書くか」という観点の規律である。
所見をどう見せるか（メッセージの並び、見出し構造）は、別ファイル `discipline_review_log_template.md` の形式の規律で定める。

両者は場面で使い分ける。

- レビュー記録ファイルに事実を残す場面では、本ファイルの四要素（箇所・現状・問題・修正後）で書く。
- 利用者に判断を仰ぐメッセージとして提示する場面では、形式の規律の「概要・問題点・選択肢・推奨」の流れで並べる。
- 同じ所見を両方の場面で扱うときは、まず四要素で事実を残し、提示時に並びを組み替える。

各所見を次の 4 要素で書く：

1. **箇所**：どのファイル・行・節か（パス + 行番号 + 節名）
2. **現状**：該当箇所の引用（実際の文言 / コードブロックで 1〜3 行）
3. **問題**：何が不整合・不適切・不足か（具体的に「何と何が違う」「何が抜けている」を書く）
4. **修正後**：どう変えるか（提案文言 / コードブロックで 1〜3 行）

クラスター単位の集約は所見一覧の概要として併用してよい。各所見の詳細は 4 要素で展開する（2 段構造：一覧の概要 → 必要に応じて個別所見へドリルダウン）。

テンプレート：

    ### {所見 ID}：{所見の一行要約}

    **箇所**：{ファイルパス}:{行番号}（{節名}）

    **現状**：
    ```
    {ファイルからの実引用、1〜3 行}
    ```

    **問題**：{何が不整合か、具体的に。抽象表現禁止}

    **修正後**（{3 択 / 単一案}）：
    ```
    {提案文言、1〜3 行}
    ```

**関連する規律：**

- レビュー所見のテンプレート（`discipline_review_log_template.md`）
- レビュー所見の必要性判定（`discipline_review_necessity_judgment.md`）
- レビュー出力の即時保存（`discipline_review_save_immediately.md`）
