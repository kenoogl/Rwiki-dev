## Round 1：要件全件の網羅

**P-1** ERROR
- 対象：Req 2 AC3（実行条件比較の契約）
- 説明：「実行条件の設定（`single`・`dual`・`dual+judgment` の 3 種別）によるステップ省略」と「実行時の障害によるステップ欠如」を区別する設計がない。比較モデルは条件不一致時に比較無効の理由を出すと定義しているが、「Step B が省略されたのは `single` という設定によるものか、実行エラーによるものか」を評価機能がどう区別して分類・集計に反映するかが設計に現れていない。
- 根拠：Req 2 AC3

**P-2** ERROR
- 対象：Req 3 AC4
- 説明：「元の証拠データが変わらなければ再計算を許可する」という要件に対し、設計が全く対応していない。分析実行の記録ファイルは評価ロジックのバージョンと入力 run 一覧を記録するが、「証拠データが変わっていないか」を判定する手段（ハッシュ比較・タイムスタンプ比較など）が未定義で、再計算の起動条件も不明。
- 根拠：Req 3 AC4

**P-3** ERROR
- 対象：Req 3 AC3
- 説明：「証拠データから指標値（以下「メトリクス」）への計算経路を保存する」について、設計は計算順序（メタデータ → 所見 → 判定単位 → 検証結果）を定義するが、この経路を分析結果ファイル（raw データから計算・生成した二次ファイル）のどのフィールドにどう記録するかが未定義。後から計算を追跡・検証できる証拠がない。
- 根拠：Req 3 AC3

**P-4** WARN
- 対象：Req 4 AC3
- 説明：留意点登録ファイルに記す留意点について、「データ品質の問題（証拠の質）」と「実行品質の問題（プロセスの問題）」を区別するための分類スキームが設計にない。例示（成熟度混在、サンプル数不足など）はあるが、どの軸で区別するかの必須フィールドが未定義。
- 根拠：Req 4 AC3

**P-5** WARN
- 対象：Req 5 AC2
- 説明：「分析結果ファイルから元の run 識別子・対象成果物識別子へのリンクを保存する」という要件について、設計は概念として言及するが、実行条件別メトリクスファイルや比較結果ファイル等の具体フィールドに `run_id` や `target_id` を持つことが明示されていない。
- 根拠：Req 5 AC2

**P-6** WARN
- 対象：Req 8 AC4
- 説明：「どのフェーズ固有の追加指標セット（以下「フェーズ別追加指標」）を適用したかを分析結果ファイルに明示する」という要件について、設計は追加指標の概念と各フェーズの例を定義するが、「この run ではどの追加指標を使ったか」をどの分析結果ファイルにどのフォーマットで記録するかが未定義。
- 根拠：Req 8 AC4

**P-7** WARN

## Round 2：アーキテクチャ整合性

**P-10** WARN
- 対象：分類モデルと比較モデルでの適格性メモの扱いの非対称
- 説明：分類の段階では「補助判断材料として参照してよいが、最終判定はメタデータ・検証結果が基礎」とし、比較の段階では「先に尊重する」としている。適格性メモが「標準比較不可」と示しつつメタデータが `valid` を示している場合、run は valid に分類されたまま比較から除外される。この非対称な優先ルールが設計の一か所で整合付けられておらず、実装者が判断に迷う。
- 根拠：設計の分類モデル、比較モデル §1

**P-11** INFO
- 対象：アーキテクチャ図（Mermaid）
- 説明：図は「runs → 取り込み → reports → 分析出力」という単純なフローのみを示しており、5 段の処理手順（取り込み → 分類 → メトリクス抽出 → 比較 → 報告）の中間フローが省略されている。設計本文の説明と図の対応が弱い。
- 根拠：Architecture セクション

## Round 3：データモデル・スキーマ詳細

**P-12** ERROR
- 対象：run 別メトリクスファイル・所見別メトリクスファイル・実行条件別メトリクスファイル・run 分類一覧ファイル
- 説明：自己改善機能と論文インターフェース機能が直接読む主要な分析結果ファイルだが、必須フィールドが設計に一切定義されていない。後続機能の実装時にインターフェースの食い違いが起きるリスクが高い。フィールド命名は「未解決の公開課題」として先送りされているが、設計ゲート通過の条件として最低限の契約が必要。
- 根拠：Req 3 AC1、Req 5 AC1

**P-13** ERROR
- 対象：実行条件別比較ファイル・フェーズ別比較ファイル
- 説明：論文インターフェース機能が一次入力として読む比較結果ファイルのフィールド仕様が未定義。実行条件の識別情報をどのフィールドに埋め込むか（P-5 とも関連）が不明のまま。
- 根拠：Req 2 AC4、Req 7 AC1

**P-14** WARN
- 対象：留意点登録ファイル（`caveat_register.json`）の必須フィールド
- 説明：除外報告ファイルは 6 フィールドを明示しているが、留意点登録ファイルは例示のみで必須フィールドが未定義。論文インターフェース機能が raw データを再読せずに留意点を継承するためには、最低限のフィールド契約が必要。
- 根拠：Req 4 AC1–AC3

**P-15** WARN
- 対象：除外報告ファイル（`exclusion_report.json`）のフィールド定義
- 説明：除外報告ファイルの必須フィールドにレビュー実施モード（`review_mode`）が含まれていない。Req 9 のモード別分析を除外集計でも行うには run 分類一覧ファイルとの結合が必要になり、除外報告ファイル単体での分析が困難になる。
- 根拠：Req 9 AC2

## Round 4：API 接合面の具体化

**P-16** WARN
- 対象：持ち込みバンドル（外部環境で収集した証拠データ一式）の取り込み契約
- 説明：持ち込みバンドルの取り込みに必要な最小ファイル群は列挙されているが、`bundle_manifest.yaml` 自体に何のフィールドが必要かが評価機能の設計内で定義されていない。出所情報の必須フィールド（ソースリポジトリ識別子、ソースリビジョン、プロトコルバージョン等）を取り込み契約として明示すべき。
- 根拠：Req 10 AC1, AC2

**P-17** WARN
- 対象：後続機能が消費するフィールドレベルの契約
- 説明：自己改善機能と論文インターフェース機能が読むファイル名は設計に列挙されているが、「それらのどのフィールドを期待するか」が現れていない。P-12/P-13 と一体の問題だが、特に自己改善機能が所見別メトリクスファイルの何を読むかは機能間の境界設計として明確化が必要。
- 根拠：Req 5 AC4

## Round 5：アルゴリズム＋性能達成手段

**P-18** WARN
- 対象：メトリクス計算式の未定義
- 説明：受理率、1 run あたりの所見数、判定ステップの呼び出し率などの計算式が未定義。たとえば「受理率の分母は全所見か、受理可能な所見のみか」が曖昧なまま実装に進むと、後から追跡不能な計算上の食い違いが生じる。Req 3 AC3 の「計算経路の保存」は計算式が明示されて初めて機能する。
- 根拠：Req 3 AC1–AC3

**P-19** WARN
- 対象：フェーズ別追加指標の選択手順
- 説明：「どのフェーズ・プロファイルにどの追加指標セットを適用するか」の選択手順が未定義。run のメタデータから自動判定するのか、設定ファイルで手動指定するのかが不明。Req 8 AC4（選択の明示）を満たすためにも必要。
- 根拠：Req 8 AC1, AC4

## Round 6：失敗モード処理＋観測性

**P-20** WARN
- 対象：破損・スキーマ違反ファイルの取り込み時処理
- 説明：取り込み時に読む証拠ファイルが破損またはスキーマ違反だった場合の動作（`analysis_blocked` 状態に遷移するか、エラーを出して処理中断するか）が設計に記載されていない。設計の「欠如と無効の区別」セクションはファイルの有無のみを対象にしており、「存在するが内容が不正」なケースを扱っていない。
- 根拠：Req 6 AC1–AC3

**P-21** WARN
- 対象：無効化の連鎖更新の具体的な手順
- 説明：「参照先の run が後から無効化された場合、その run を入力に含む分析結果ファイルに陳腐化フラグを付けるか再生成する」と定義されているが、「無効化をいつ誰がどのプロセスで検出し、陳腐化フラグを付けるか」の具体的な手順（定期バッチか、評価起動時の自動確認かなど）が未定義。foundation Req 6 AC9 の伝播義務を実際に果たせるかが担保できない。
- 根拠：Req 5 AC6、foundation Req 6 AC9

## Round 7：セキュリティ・プライバシー

**P-22** WARN
- 対象：持ち込みバンドルの内容完全性の検証
- 説明：外部環境から持ち込むバンドルの内容がすり替えられていないことの検証（チェックサム・ハッシュ照合など）が取り込み契約に含まれていない。ソースリポジトリ識別子とソースリビジョンは出所情報として記録するが、バンドル内容の改ざん検知手段がない。研究データの信頼性に関わる。
- 根拠：Req 10 AC2

**P-23** INFO
- 対象：分析結果ファイルへのアクセス制御
- 説明：内部研究ツールのため重大度は低いが、`experiments/analysis/` 以下には研究仮説に関わる中間成果物が集積するため、将来的なアクセス制御要件の欠如として認識しておく。
- 根拠：一般的なセキュリティ設計原則

## Round 8：依存選定

**P-24** INFO
- 対象：`v2/` オプション取り込みファイルの定義元
- 説明：`v2/review_artifact.json`・`v2/metric_snapshot.json`・`v2/trace_note.json` はオプション取り込みとして参照されているが、これらを定義する仕様（runtime spec か v2-acquisition spec か評価仕様自身か）が明示されていない。後続実装で依存関係が曖昧になるリスクがある。

- 根拠：foundation Req 3 AC1

## 観点別発見要約

- **Round 6（失敗モード処理＋観測性）**：破損ファイル時の取り込み処理未定義（WARN）と無効化連鎖更新の具体的手順未定義（WARN）の 2 件。foundation Req 6 AC9 への対応が設計レベルで不完全。

- **Round 9（テスト戦略）**：記述が皆無（P-26 ERROR）。分類ルールとメトリクス計算の検証可能性を設計時点で担保する必要がある。
- **Round 10（移行戦略）**：評価ロジック更新時の再処理方針未定義（WARN 1 件）。バージョン記録の仕組みはあるが再処理の手順が伴っていない。

## 主役発見への判定

### P-1（ERROR, Req 2 AC3）実行条件ステップ省略 vs 実行障害の区別

- 敵対役反論：部分的。メトリクスで部分捕捉可能だが機械的分離は未設計。ERROR 妥当。
- **判定：must-fix**
- 根拠：AC3 は「区別する」ことを要求する。設計上、run 分類やメトリクス抽出で「Step B が設計上ない（`single`）」と「Step B が失敗で欠如した」を弁別する判定ルールが存在しない。比較結果の信頼性に直結する。敵対役反論は同意しており採否不要。

### P-2（ERROR, Req 3 AC4）再計算の許可

- 敵対役反論：全面。AC4 は「許可する」であり「変更を検知する」ではない。immutable raw + 物理分離 + manifest で構造的に充足。
- **判定：leave-as-is（敵対役反論を採用、所見撤回）**
- 根拠：AC4 の文言は "allow re-computation when schema-compatible raw evidence is unchanged" であり、変更検知機構を要求してはいない。raw が immutable（Decision 1）で analysis が物理分離されている以上、同じ入力に対して再計算を実行できる状態は設計として成立している。主役は「許可」を「検知」に読み替えた過剰解釈。

### P-3（ERROR, Req 3 AC3）計算経路の保存方法

- 敵対役反論：部分的。計算順序は定義済み、フィールド名は Open Issues に先送り。ERROR → WARN。
- **判定：should-fix**
- 根拠：AC3 は "preserve the derivation path" を要求する。計算の一次入力順序（metadata → findings → decision units → validation artifacts）は定義されているが、分析結果ファイル内に「この値はどの入力からどう算出したか」を追跡可能にする構造的な仕組み（参照フィールド、算出元一覧など）が定義されていない。フィールド名の最終確定は Open Issues でよいが、構造の骨格は設計段階で示すべき。

### P-4（WARN, Req 4 AC3）留意点の分類軸

- 敵対役反論：部分的。除外報告（run 品質）と留意点登録（報告用）の構造的二分はある。留意点登録内部の軸のみ未定義。
- **判定：should-fix**
- 根拠：敵対役の指摘する構造的二分は認めるが、AC3 は留意点自体を「データ品質」と「実行品質」で区別することを要求している。留意点登録ファイル内にこの軸のフィールドが必要。

### P-5（WARN, Req 5 AC2）分析結果ファイルの run・対象識別子リンク

- 敵対役反論：部分的。除外報告には `run_id` あり。メトリクス・比較ファイルのみ未明示。
- **判定：should-fix**
- 根拠：除外報告での対応は認めるが、メトリクスファイルや比較ファイルが「run → 計算値」のリンクを持つことを明示すべき。

### P-6（WARN, Req 8 AC4）フェーズ別追加指標の適用記録

- 敵対役反論：部分的。`phase_metric_profile_version` が分析セット単位で部分充足。
- **判定：should-fix**
- 根拠：分析セット単位のバージョン記録は認めるが、AC4 は "make phase-specific metric selection explicit in derived artifacts" であり、個々の比較・メトリクス出力に「どの overlay を適用したか」が明示されるべき。

### P-7（WARN, Req 9 AC4/AC5）実施モード混在フラグと引き渡し境界

- 敵対役反論：部分的。AC6 の標準集団ルール明文化は評価済みだが AC4/AC5 フィールド欠如は同意。
- **判定：should-fix**

### P-8（WARN, Req 10 AC5）持ち込み証拠の分析結果追跡

## 敵対役独立発見への判定

### A-1（ERROR, Req 2 AC6）プロトコル/プロンプトバージョン混在の検出・報告

- **判定：should-fix**
- 根拠：設計の比較モデル §1 に「protocol/runtime/prompt/schema version が比較可能」を前提とし、不一致なら `comparison_invalid_reason` を出すとある。これは検出と報告の骨格を含んでいる。ただし AC6 が強調する「per-run メタデータが全て揃い整形式であっても混在を検出する」という特殊ケースに対し、検出手順と報告先（`comparison_invalid_reason` に加えて `caveat_register` にも出すのか等）の明確化が必要。ERROR は過大で should-fix。

### A-2（ERROR, Req 10 AC4）受理ルール本体の判定ロジック未定義

- **判定：must-fix**
- 根拠：設計は受理の 3 状態（`admitted_standard` / `admitted_exploratory` / `rejected`）を列挙するが、「何が揃えば admitted_standard、何が欠ければ rejected」という決定ルールが一切ない。実装者はこのルールなしに受理処理を書けない。P-16（manifest フィールド）とは独立の問題。

### A-3（WARN, Req 6 AC4）hard failure vs exploratory partial analysis の区別

- **判定：should-fix**
- 根拠：AC4 は "distinguish hard failure from exploratory partial analysis" を要求する。`analysis_blocked` は hard failure に相当するが、「探索的部分分析」という実行モードが設計に存在しない。optional intake が読めなくても標準分析は成立するとあるが、これは入力縮退であって AC4 の求める「探索的に部分分析を行うモード」とは別の概念。

### A-4（WARN, Req 9 AC3）手動レビュー記録契約への適合検証

- **判定：should-fix**
- 根拠：AC3 は "shall not treat ordinary editing activity as valid review evidence unless it is recorded through the manual review record contract" と明記する。設計が `review_mode` メタデータを無検証で信頼するだけでは、AC3 の排除義務を果たす手段がない。manual_dogfooding 記録が契約の構造要件を満たしているかの最低限の検証ルールを定める必要がある。

### A-5（WARN, Req 7 AC4）design/tasks 最高価値仮説の検証可能性

- **判定：should-fix**
- 根拠：AC4 は仮説検証に「十分な情報を保持する」ことを要求する。汎用カウント指標（所見数・受理率）ではフェーズ間の「価値」を比較できない。フェーズ別追加指標は概念のみで先送りされており、仮説検証に必要な指標構成を導出できない。最低限「価値」の操作的定義と対応指標の方針が必要。

### A-6（WARN, Req 2 AC4）全比較関連出力での実行条件可視化

- **判定：should-fix**
- 根拠：AC4 は "all comparison-relevant derived outputs" での可視化を求める。run 別・所見別メトリクスファイルが比較スライスに使われる場合、これらにも実行条件フィールドを保持する必要がある。

### A-7（WARN, runtime 副産物への未宣言契約依存）

- **判定：must-fix**
- 根拠：`comparison_eligibility_note.json` は分類と比較の双方で参照され、評価機能の中核判定に関与する。にもかかわらず、このファイルのスキーマを定義する spec が宣言されておらず、foundation の 5 スキーマにも含まれない。安定契約なしに中核挙動が依存する状態は、spec 間の境界違反であり設計ゲートの阻害要因。
