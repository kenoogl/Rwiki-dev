## 第1ラウンド：基本整合性

**P-1 ERROR / 要件2 受入条件2 「対象レイヤー列挙の "policy" が未定義」**

- 対象箇所：Requirement 2 AC2（受入条件2）の "targeted layer at minimum among prompt, policy, schema, runtime, or workflow"
- 説明："policy" という言葉は本仕様書にも上流の基盤仕様書にも定義がない独自の語。他の4語（prompt／データ構造定義（schema）／実行基盤（runtime）／workflow）は対応する概念が他の仕様書に存在するが、"policy" だけ定義のないまま宙に浮いている。実装者が異なる解釈をとる恐れがある。
- 根拠：基盤仕様書に "policy" に相当する抽象定義がなく、本仕様書内にも説明がない。

**P-2 ERROR / 要件3 受入条件1 「再実行と後退テストの分岐基準が同語反復で空虚」**

- 対象箇所：Requirement 3 AC1 "shall define when replay is required and when lighter backtest is sufficient"
- 説明：再実行検証（replay＝記録済みの証拠を使って同じ手順を再現すること）と後退テスト（backtest＝改善案を過去のデータに当てはめて事後評価すること）のどちらを使うかを「定義せよ」と書くだけで、判断基準の要素（変更の規模・対象レイヤー・リスクの大きさなど）を一切示していない。実装者はこの受入条件をどう満たせばよいか判断できず、検証も不可能。
- 根拠：受入条件は検証可能な条件を示すべきだが、この条件は「何かを定義する義務があること」だけを述べており、その中身を委任先に丸投げしている。

**P-3 ERROR / 要件4 受入条件1 「改善提案の状態遷移が不完全（初期状態・遷移の引き金が欠落）」**

- 対象箇所：Requirement 4 AC1 "define explicit states for proposal review, approval, rejection, and adoption"
- 説明：列挙された4状態（査読中・承認・却下・採用）に「提案が作成された直後（下書き／提出済み）」の初期状態がない。また各状態に移行するきっかけとなる出来事（誰が何をしたら状態が変わるか）が一切記述されていない。これでは状態機械（状態の流れを管理する仕組み）として実装できない。
- 根拠：状態の名前を列挙するだけでは状態機械を定義したことにならない。要件4 受入条件2では「人間の承認が必要」と述べるが、どの状態遷移に対して何が必要かは受入条件1が担うべき情報。

**P-4 WARN / 要件4 受入条件4 「"バージョン更新" の対象が曖昧」**

- 対象箇所：Requirement 4 AC4 "require version updates for adopted runtime-affecting changes"
- 説明：基盤仕様書 要件6 受入条件2は、プロトコル版数・プロンプト版数・実行基盤版数など複数のバージョン系列を定義している。どのバージョンを更新しなければならないかが特定されていないため、実装が分岐する可能性がある。
- 根拠：基盤仕様書 要件6 受入条件2が複数のバージョン系列を定義しており、曖昧さが実装の違いに直結する。

**P-5 WARN / 要件5 受入条件4 「"通常の置き換え" が未定義」**

- 対象箇所：Requirement 5 AC4 "The feature shall distinguish rollback from ordinary supersession"
- 説明：差し戻し（rollback＝採用した変更を元に戻すこと）と対比される "ordinary supersession（通常の置き換え）" の意味が仕様書内で説明されていない。改善提案の流れの中でどのような置き換えが "通常" とみなされるか不明。
- 根拠：提案の流れを管理する語彙として初出かつ未定義。

**P-6 WARN / 要件1 受入条件3 「無効な実行記録を入力として使う際の制約がない」**

- 対象箇所：Requirement 1 AC3 "support inputs from valid runs and invalid runs while preserving that distinction"
- 説明：基盤仕様書 要件6 受入条件5は「メタデータだけで無効な実行記録を除外できるようにする」ことを目的として定義された。自己改善機能が無効な実行記録を改善の入力として受け入れる場合、その記録が示す品質の信号がどれだけ信頼できるかについての制約が存在しない。意図的な設計判断であれば、その理由を仕様書に記載すべき。
- 根拠：基盤仕様書 要件6 受入条件5（無効記録の除外支援が設計目的）との設計意図の緊張。

## 第2ラウンド：上流文書照合

**P-7 ERROR / 境界定義 ＋ 全体 「依存するデータ構造定義が名前で参照されていない」**

- 対象箇所：境界定義 "dual-reviewer-foundation の schema and metadata contract に依存する"
- 説明：基盤仕様書の隣接仕様との期待値では、自己改善機能が `finding`（指摘）・`necessity_judgment`（必要性判定）・`review_case`（レビュー事例）という3つのデータ構造定義に依存すると名指ししている。しかし自己改善仕様書のどの受入条件にもこれらの名前が登場しない。依存関係を宣言しただけで、どのフィールドをどの目的で使うかの結びつきがないため、実装が基盤のデータ構造から離れても気づけない。
- 根拠：基盤仕様書 要件3 受入条件4・5・6が定義するフィールドが、自己改善側の受入条件に反映されていない。

**P-8 ERROR / 要件2 「改善提案の記録に実行フェーズ・実験条件区分のフィールドがない」**

- 対象箇所：Requirement 2（改善提案の記録の契約）全体
- 説明：基盤仕様書 要件1 受入条件8・9は、実行フェーズ（phase/profile＝論文のどの段階を審査するかを示す分類）と実験条件区分（treatment＝どの比較条件でレビューを実施するかを示す区分値）の語彙の管理を実行基盤仕様書に委ねつつ、下流の仕様書がこれらを索引として扱う前提を置いている。改善提案が特定の実行フェーズ・実験条件区分でのみ現れる観察に基づく場合、提案の記録にそのコンテキストがないと適用範囲が不明確になる。
- 根拠：基盤仕様書 要件1 受入条件8・9。

**P-9 ERROR / 要件2 「改善提案のデータ構造定義がバージョン管理されたリポジトリ内資産として指定されていない」**

- 対象箇所：Requirement 2 AC1 "define a structured proposal unit"
- 説明：「構造化された改善提案の単位」は実質的に新しいデータ構造定義だが、基盤仕様書 要件7 受入条件1（「すべてのデータ構造定義はリポジトリの中に置く」）および 要件3 受入条件3（「データ構造定義はバージョン管理した成果物とする」）の適用を明示する受入条件が存在しない。改善提案が非定形の記述形式で実装される余地が残っている。
- 根拠：基盤仕様書 要件7 受入条件1、要件3 受入条件3。

## 第3ラウンド：本質的観点

**P-10 ERROR / 要件3 全体 「"再実行検証" と "後退テスト" が定義されていない」**

- 対象箇所：Requirement 3（再実行検証と後退テストの要件）全体
- 説明：要件3の受入条件すべてが再実行検証（replay）と後退テスト（backtest）を前提としているが、どちらの言葉も本仕様書内で定義されていない。再実行検証は「同じ入力で処理をやり直すこと」なのか「記録済みの証拠を使った模擬」なのか判断できない。後退テストが「軽量」とされる根拠も不明。定義がなければ受入条件を検証する基準として機能しない。
- 根拠：要件3 受入条件1〜5が参照する中心的な概念が未定義のまま。

**P-11 WARN / 要件1 受入条件1 「"有効な改善入力の分類" を列挙していない」**

- 対象箇所：Requirement 1 AC1 "define valid improvement input classes"
- 説明：受入条件1が「分類を定義せよ」と指示するだけで、要件書内で分類の一覧を示していない。受入条件2（品質証拠と作業失敗証拠の区別）が示唆を与えるが、確定した分類表がない。設計段階に委任するなら明示的にその旨を記載すべき。
- 根拠：要件書は「何を実現するか（WHAT）」を確定させる役割を持つが、分類の中身が曖昧なまま委任されている。

**P-12 WARN / 要件4 受入条件2 「実行基盤に影響しない変更の採用経路が未定義」**

- 対象箇所：Requirement 4 AC2 "require human approval before runtime-affecting changes are adopted"
- 説明：「実行基盤に影響する変更」には人間の承認を求めるが、それ以外の変更（例：説明文書の更新・履歴記録のみの追加）の採用経路が未定義。自動採用が許容されるのか、それともすべての採用に人間の承認が必要なのか判断できない。
- 根拠：受入条件2の適用範囲が明確でない。

## 第4ラウンド：例外系（失敗モード・並行処理・安全性・観測・差し戻し・規模）

**P-13 ERROR / 全体 「採用後に根拠となった記録が無効化された場合の対応要件がない」**

- 対象箇所：要件1 受入条件5（証拠の出所保存）、要件4 受入条件3（採用変更と提案の紐付け）
- 説明：採用済みの改善提案の根拠となった実行記録が、採用後に無効とされた場合の対処が未定義。改善提案の有効性を再評価する引き金となる要件がなく、根拠を失った改善が実行基盤に残り続けるリスクがある。
- 根拠：基盤仕様書 要件6 受入条件3・4は無効化の印を付ける仕組みを定義しており、自己改善機能はこの仕組みを活用する責任がある。

**P-14 WARN / 要件2 「同一の部品を対象とする複数の改善提案の競合解決が未定義」**

- 対象箇所：Requirement 2（改善提案の記録の契約）全体
- 説明：同じプロンプトファイルや同じデータ構造定義のフィールドを対象とする複数の改善提案が同時に査読中の状態にある場合、採用順序や相互干渉の解決規則が存在しない。採用される順番次第で逆方向の変更が入る可能性がある。
- 根拠：並行する提案は状態機械の未定義のケースとして扱われていない。

**P-15 WARN / 要件8 「外部から取り込む証拠の品質確認・リスク評価の要件が欠如」**

- 対象箇所：Requirement 8（外部証拠の出所保存）全体
- 説明：外部バンドルから取り込んだ証拠がそのまま改善提案の根拠として使われる経路が定義されているが、取り込み時の品質確認や不審なコンテンツのリスクを評価する要件がない。外部証拠に基づく提案が採用されると、内部経路より品質保証が低い状態で実行基盤が変化する可能性がある。
- 根拠：要件8 受入条件5は「出所が不十分な外部証拠を標準的な比較証拠と同等視しない」と求めるが、その判定を行う手続きへの要件がない。

**P-16 WARN / 要件5 「採用前に差し戻し可能かどうかを確認する要件がない」**

- 対象箇所：Requirement 5（差し戻しと失敗への対処）全体
- 説明：差し戻しの発動条件（受入条件1）と理由の保存（受入条件3）は定義されているが、変更を採用する前に「その変更が実際に差し戻せるか」を検証する要件がない。採用後に差し戻し不能と判明するケース（例：依存する変更が連鎖している場合）に対処できない。
- 根拠：差し戻し可能性の確認は採用の流れ（要件4）の一部として要件化されるべき。

## 第5ラウンド：波及精査

**P-17 WARN / 要件6 受入条件3 「"証拠の品質" カテゴリが評価仕様書の領域と重複する可能性」**

- 対象箇所：Requirement 6 AC3 "preserve whether an improvement is motivated by runtime quality, workflow quality, or evidence quality"
- 説明：「証拠の品質」を改善の動機カテゴリとして自己改善機能が分類することは、評価の基準定義を評価仕様書（dual-reviewer-evaluation）の範囲外（Out of Scope）として切り出した設計と衝突する可能性がある。証拠の品質を自己改善機能が判断するとき、評価仕様書との境界が曖昧になる。
- 根拠：自己改善仕様書の境界定義 Out of Scope「evaluation metric definition itself（評価指標の定義そのもの）」と矛盾しうる。

**P-18 WARN / 要件7 ＋ 要件8 「外部から取り込む証拠のレビュー方式の分類語彙が不完全」**

- 対象箇所：Requirement 7（人手確認と自動実行の証拠の出所区別）、Requirement 8（外部証拠の出所保存）
- 説明：基盤仕様書 要件6 受入条件6が定義するレビュー方式の語彙は、「開発者自身によるテスト使用（manual dogfooding）」と「実行基盤を経由した自動レビュー（runtime-mediated）」の2種のみ。外部プロジェクトから取り込んだ証拠が「外部プロジェクトでの開発者自身によるテスト使用から生成された」場合、現在の語彙では分類できない。要件8 受入条件4は「レビュー方式の出所を失わない」と求めるが、その出所の分類語彙が基盤仕様書側で網羅されていないため、要件が宙に浮いたまま実装に委ねられる。
- 根拠：基盤仕様書 要件6 受入条件6（語彙定義の責任が基盤仕様書にある）と要件8 受入条件4の整合。

## パート1：主役の各発見への反論

**P-1（要件2 受入条件2 "policy" 未定義）**
- 対象：Requirement 2 AC2
- 判断：反論あり（部分的）
- 内容：主役は「他の4語は対応概念があるが policy だけ宙に浮く」と述べるが、これは正確でない。"workflow" も基盤仕様書に抽象定義はなく、本仕様書内の要件1 受入条件2・要件6 受入条件3で動機カテゴリとして使われているにすぎない。"runtime" も提案の対象レイヤー名としては同程度に非形式的である。AC2 は "at minimum among"（少なくとも以下のうち）という非網羅的な例示列挙であり、確定分類表ではない。よって "policy" 単独を ERROR とするのは過大で、レイヤー分類の確定を設計に委ねる旨を明記すべき、という WARN 相当の指摘が妥当。

**P-2（要件3 受入条件1 同語反復）**
- 対象：Requirement 3 AC1
- 判断：反論あり（部分的）
- 内容：欠陥の種類（判断基準を示さず委任）は実在する。しかし本仕様書には "shall define X" 形式の受入条件が多数あり（要件1 受入条件1、要件2 受入条件1 など）、主役自身はそれらを WARN（P-11）や別観点（P-9）で扱っている。構造的に同型の条件のうち AC1 だけを ERROR とするのは深刻度の較正が一貫しない。WARN とし、後述の系統的パターンとして束ねるべき。

**P-3（要件4 受入条件1 状態遷移の不完全）**
- 対象：Requirement 4 AC1
- 判断：反論あり（部分的）
- 内容：主役が挙げる「初期状態（下書き／提出済み）」「遷移の引き金」は要件書ではなく設計書の領域への踏み込みで、これ自体を要件欠陥とするのは過剰。ただし主役が弱くしか論じていない核心は別にある。AC1 の4状態と、要件3 受入条件4（「未支持」と「未検証」の区別）・要件5 受入条件4（差し戻しと通常置き換えの区別）が含意する追加状態とが整合しない、という状態集合の内部不整合である。指摘の方向は正しいが論拠が弱い。

**P-4（要件4 受入条件4 "バージョン更新" 曖昧）**
- 対象：Requirement 4 AC4
- 判断：反論あり（部分的）
- 内容：どのバージョンを更新するかは、要件2 受入条件2 の対象レイヤー（プロンプト／データ構造定義／実行基盤など）から合成的に導ける（プロンプト変更ならプロンプト版数）。よって「実装が分岐する」という主役の表現は誇張。要件2 受入条件2 との対応を明示せよ、という明確化注記にとどめるべき。

**P-5（要件5 受入条件4 "通常の置き換え" 未定義）**
- 対象：Requirement 5 AC4
- 判断：反論あり（部分的）
- 内容：置き換え（supersession）は一般語として文脈から判別可能（差し戻しは失敗駆動の事後巻き戻し、置き換えは前向きの正常更新）であり、初出未定義語というだけで欠陥とするのは過敏。真の問題は、AC4 が「両者を区別せよ」と命じるのに区別の判定基準（弁別子）を与えていない点であり、欠陥の焦点を語の新規性から弁別子の欠落へ再定義すべき。

**P-6（要件1 受入条件3 無効記録入力の制約なし）**
- 対象：Requirement 1 AC3
- 判断：反論あり
- 内容：これは基盤仕様書 要件6 受入条件5 の範囲の読み違い。同条件は「品質指標から無効記録を除外する」ことを支援するもので、無効記録の全面禁止ではない。本仕様書 要件1 受入条件2 は品質証拠と作業失敗証拠を区別しており、無効記録は作業失敗証拠としては正当な入力である。AC3 の "while preserving that distinction"（その区別を保ったまま）の節がまさに制約に当たる。矛盾も制約欠落も成立しない。

**P-7（依存データ構造定義が名前で参照されていない）**
- 対象：境界定義 ＋ 全体
- 判断：反論あり（部分的）

**P-9（要件2 受入条件1 改善提案のデータ構造定義が管理外）**

**P-10（要件3 全体 "再実行検証"・"後退テスト" 未定義）**

**P-16（要件5 採用前に差し戻し可能性を確認する要件がない）**

**P-17（要件6 受入条件3 "証拠の品質" が評価仕様書と重複）**

**P-18（要件7＋8 外部取り込み証拠のレビュー方式語彙が不完全）**

## パート2：主役が見落とした独立発見

**A-1 ERROR / 要件4 受入条件2・3 「承認者の同一性が記録・分離されない」**
- 対象：Requirement 4 AC2／AC3
- 説明：人間承認を要求するが、承認者が提案者と別人であるべき制約も、誰がいつ承認したかの識別記録の要件もない。基盤仕様書 要件1 受入条件5・要件6 受入条件2 は「人間サインオフ状態」を持つが、自己改善側はそれを承認者の身元・時刻に結びつける要件を欠く。受入条件3 は提案と変更の紐付けのみで承認者を辿れない。
- 根拠：基盤仕様書 要件6 受入条件2（人間サインオフ状態）と要件4 受入条件3 の追跡可能性の不整合。

**A-2 WARN / 要件8 受入条件2 「出所フィールド名が基盤の正典名に束ねられていない」**
- 対象：Requirement 8 AC2
- 説明：取得元リポジトリ識別と取得元版数の保持を求めるが、基盤仕様書 要件6 受入条件7 が定義する「正典的な出所フィールド名」を参照する受入条件がない。評価側の証拠取り込みと自己改善側でフィールド名が分岐し、同一出所が別名で記録される恐れがある。
- 根拠：基盤仕様書 要件6 受入条件7（正典フィールド名の責任が基盤側）。

**A-3 ERROR / 要件3 受入条件3 「再実行・後退テスト成果物にメタデータ束縛がない」**
- 対象：Requirement 3 AC3
- 説明：再実行・後退テストの結果を生の実行証拠と別成果物として保存せよと求めるが、その成果物自体がどのプロトコル版数・プロンプト版数・実行基盤版数の下で実行されたかを束ねる要件がない。後退テスト結果は事実上レビュー類似の実行であり、基盤仕様書 要件6 受入条件2 のメタデータに束ねられないと後から検証も無効化もできない。
- 根拠：基盤仕様書 要件6 受入条件2・受入条件4（必須メタデータ欠落は検証失敗）の枠が再実行・後退テスト成果物に適用されていない。

**A-4 WARN / 要件5 受入条件1 「差し戻し条件を観測・評価する主体と時点が未定義」**
- 対象：Requirement 5 AC1
- 説明：差し戻しの発動条件を定義せよと求めるが、その条件を誰が・いつ監視し評価するか（継続監視か、次回実行時か、評価信号受領時か）の要件がない。観測要件を欠くと条件は定義されても発火しない死んだ要件になる。P-13 は根拠記録の無効化という特定事象に限るが、本件は発火判定機構そのものの不在で範囲が異なる。
- 根拠：要件5 受入条件1 が条件のみを定義し、その評価契機を規定していない。

**A-5 WARN / 要件2 受入条件4 ＋ 要件3 「期待便益が後退テスト結果と照合されない」**
- 対象：Requirement 2 AC4
- 説明：提案に期待便益と想定リスクを記録せよと求めるが、その期待便益を要件3 の後退テスト結果と照合する義務も、便益が実現しなかった場合に要件5 の差し戻しへつなぐ要件もない。主張された便益が検証結果と乖離したまま採用が残存しうる。
- 根拠：要件2 受入条件4・要件3・要件5 の間に便益→検証→差し戻しの連結要件が欠落。

**A-6 WARN / 要件6 受入条件4 「強制力のない禁止条項」**
- 対象：Requirement 6 AC4
- 説明：「文書化されていない物語駆動の変更を定常動作に入れない」と禁止するが、"文書化されていない"・"物語駆動" を判定する手続きも、要件4 の承認の流れとの接続もない。検査・関門が規定されないため、執行不能な宣言にとどまる。P-2／P-10 とは対象受入条件が異なり、論点も「執行可能性」で独立。
- 根拠：要件6 受入条件4 が禁止のみを述べ、検出・関門の受入条件を伴わない。

**A-7 ERROR / 要件1 受入条件5・要件5 受入条件2・要件8 「出所欠落時の失敗挙動が非対称に未定義」**
- 対象：Requirement 1 AC5／Requirement 5 AC2／Requirement 8
- 説明：出所（provenance）の保持を繰り返し要求するが、出所が欠落・断絶した場合の結果（提案を却下・凍結するなど）を定義する受入条件がない。基盤仕様書 要件6 受入条件4 は「必須メタデータ欠落は検証失敗」という失敗挙動を持つのに、自己改善側にはこれに対応する「出所欠落→提案を阻止」規則がなく、出所が無言で欠けたまま提案が進む非対称が生じる。
- 根拠：基盤仕様書 要件6 受入条件4 との失敗挙動の非対称。
